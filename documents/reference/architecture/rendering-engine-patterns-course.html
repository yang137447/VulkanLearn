00. 分类地图

模式可以按问题层级来记。GoF 23 种只是其中一层；做渲染引擎时，更常碰到的是资源生命周期、GPU 同步、数据驱动、材质系统、渲染图、缓存和多线程协作。

大类 关注点 典型例子
GoF Design Patterns 类、对象、接口之间如何协作。 Factory Method、Builder、Observer、Strategy、Facade。
Architecture Patterns 系统整体如何分层、通信和组织模块。 ECS、Scene Graph、Render Graph、Event Bus、Plugin System。
Rendering Patterns 渲染流程、材质、pass、shader、GPU 资源如何组织。 Material Instance、Render Queue、Pipeline Cache、Shader Reflection。
Data Patterns 场景、资源、组件、配置如何表达和传递。 DTO、Snapshot、Handle、Prefab、Versioned Data。
Performance Patterns 如何减少 CPU、GPU、内存和同步开销。 Cache、Batching、Instancing、LOD、Arena、Ring Buffer。
C++ Idioms 如何用 C++ 安全高效地表达资源和抽象。 RAII、Move Semantics、PImpl、CRTP、Rule of Five。
Concurrency Patterns 多线程、异步加载、任务调度如何协作。 Job System、Producer-Consumer、Thread Pool、Double Buffered State。
Vulkan / GPU Patterns 命令缓冲、描述符、同步、帧资源如何管理。 Frames in Flight、Deletion Queue、Descriptor Allocator、Barrier Helper。
记忆原则：先记“它解决哪个引擎问题”，再记名字。比如 RAII 不是“C++ 术语”，而是“CPU 侧对象生命周期怎么自动收口”；Deferred Destruction 不是“销毁队列”，而是“GPU 还没用完资源时不能马上释放”。

01. 学习方法

这份教材建议按问题学习，而不是按百科条目背诵。每个模式都要放回渲染引擎里的具体系统：Pipeline、Material、Render Graph、Scene、Asset、Frame Resource 或 GPU Sync。

1. 痛点 先描述不用模式会出现什么具体问题。
2. 名字 再把问题和模式名关联起来。
3. 结构 拆出核心对象、数据和所有权关系。
4. 引擎落点 找到它在 VulkanLearn 中可能出现的位置。
5. 边界 写清什么时候不该用，避免为了模式而模式。
问题优先

先问痛点

例如“Pipeline 创建参数太多且重复”会自然引出 Builder 和 Pipeline Cache。

系统落点

再找代码位置

把模式绑定到具体系统：RenderGraph、PipelineFactory、MaterialInstance、SceneLoader。

边界意识

记录代价

每个模式都会增加某种复杂度，笔记里必须写“什么时候不用”。

02. 推荐学习路线

渲染引擎的学习顺序应该从生命周期开始，再到对象创建、渲染流程、数据驱动、性能规模化，最后进入多线程和工具链。

Phase 1
资源生命周期
RAII用 C++ 对象生命周期自动释放 CPU 侧资源。
Rule of Five / Move明确 Vulkan handle wrapper 的移动和析构规则。
Handle Pattern用 ID 引用资源，避免裸指针悬空。
Deferred Destruction等待 GPU 完成后再真正销毁资源。
Phase 2
对象创建
Factory / Builder创建不同类型资源，分步骤构建复杂 pipeline。
Pipeline Cache用稳定 key 复用昂贵的 pipeline 对象。
Descriptor Allocator集中管理 descriptor pool 和 descriptor set 分配。
Shader Reflection从 shader 反射绑定信息，减少手写错误。
Phase 3
渲染流程
Render Pass Pattern每个 pass 负责一段渲染逻辑。
Render Graph声明资源读写，让图管理顺序和生命周期。
Resource State Tracking跟踪 layout/access/stage 以辅助同步。
Debug Marker让 RenderDoc、Nsight、Tracy 中的 GPU 工作可读。
Phase 4
数据驱动
DTO把 JSON 配置映射为简单数据结构。
Material Instance材质模板和实例参数分离。
Dirty Flag只在数据变化后重新计算或上传。
Versioned Data给 JSON/schema 留出演进空间。
Phase 5
性能规模化
Arena / Ring Buffer高效处理每帧临时内存和动态 buffer。
Render Queue / Sorting Key减少状态切换，控制透明/不透明顺序。
Batching / Instancing减少 draw call。
Culling / LOD控制不可见对象和远景成本。
Phase 6
多线程工具链
Job System把 culling、animation、import 等任务并行化。
Producer-Consumer加载线程生产，渲染线程消费。
Hot Reload运行时替换 shader/material/texture。
Command + Snapshot支撑编辑器撤销和场景回滚。

03. GoF 设计模式

GoF 模式适合回答“对象之间怎么协作”。在渲染引擎里，它们经常出现在资源创建、材质系统、渲染流程、编辑器操作和事件通知中。

创建型

Pattern 一句话 渲染引擎用途 优点 代价
Singleton 单例保证一个类只有一个实例并提供全局访问点。日志、全局配置、统计信息，慎用于 Renderer/Device。访问方便，初始化集中。隐藏依赖，测试困难，生命周期和线程安全容易出问题。
Factory Method 工厂方法把具体对象创建延迟到子类或具体工厂。创建 Texture、Buffer、Shader、Pipeline、PlatformWindow。调用方不依赖具体类型。类数量增加，简单场景显得啰嗦。
Abstract Factory 抽象工厂创建一组相关对象而不暴露具体实现。Vulkan/DX12/Metal 后端分别创建 RHI 对象族。保证同一后端对象族一致。增加新产品类型比较麻烦。
Builder 建造者分步骤构建复杂对象。GraphicsPipelineBuilder、RenderPassBuilder、DescriptorLayoutBuilder。构建参数清晰，避免超长构造函数。对象简单时会显得过度设计。
Prototype 原型通过复制已有对象创建新对象。材质实例从材质模板克隆，Prefab 实例化。复用默认配置，创建成本低。深拷贝、GPU 资源和句柄所有权要小心。

结构型

Pattern 一句话 渲染引擎用途 优点 代价
Adapter 适配器把不兼容接口转换成目标接口。封装 SDL、Assimp、stb、ImGui、VMA。复用第三方库，隔离外部 API。适配层设计不好会泄漏外部概念。
Bridge 桥接把抽象和实现分离，让二者独立变化。Renderer API 与 Vulkan/DX12/Metal 后端分离。后端可替换，抽象层稳定。过早抽象会拖慢学习项目迭代。
Composite 组合用树形结构统一处理单个对象和组合对象。Scene Graph、UI Tree、Pass Group。父子层级自然，遍历统一。复杂场景下更新传播成本高。
Decorator 装饰器不改原类，动态叠加功能。Debug Renderer、Profiler Wrapper、Validation Wrapper。比继承灵活，功能可组合。多层包装后调用链和调试复杂。
Facade 外观为复杂子系统提供简单入口。Renderer::renderFrame、AssetSystem::load、RenderGraph::execute。降低使用门槛，隔离内部复杂度。外观容易膨胀成全能对象。
Flyweight 享元共享大量对象的公共状态。共享 Mesh、Material、Shader、Pipeline、Sampler。降低内存和创建成本。需要拆分共享状态和实例状态。
Proxy 代理通过代理控制真实对象访问。Lazy Texture、Streaming Resource、Placeholder Material。可加入懒加载、缓存和占位逻辑。真实对象生命周期和线程状态更复杂。

行为型

Pattern 一句话 渲染引擎用途 优点 代价
Chain of Responsibility 责任链请求沿处理链传递直到被处理。输入事件分发、资源路径 fallback、importer fallback。发送者和处理者解耦。请求可能无人处理，调试链路较长。
Command 命令把请求封装成对象。Render Command、Editor Command、Undo/Redo、任务队列。可排队、撤销、记录、跨线程传递。命令类型可能很多。
Interpreter 解释器定义语法并解释表达式。简单材质表达式、控制台命令、小型规则 DSL。适合小语言和规则系统。复杂语法应改用 parser 或脚本语言。
Iterator 迭代器统一遍历集合而不暴露内部结构。遍历组件、资源表、场景节点、render queue。封装容器结构。注意迭代器失效规则。
Mediator 中介者用中介对象管理多个对象交互。编辑器面板互相联动、工具窗口协调。减少对象之间直接依赖。中介者容易变成复杂中心。
Memento 备忘录保存并恢复对象状态。编辑器撤销、场景快照、材质参数回滚。不破坏封装即可恢复状态。快照可能占内存，GPU 资源不能简单拷贝。
Observer 观察者一个对象变化时通知依赖者。resize、asset hot reload、config change、scene change。扩展方便，适合事件驱动。生命周期、通知顺序和递归通知容易出错。
State 状态对象行为随内部状态变化。Resource Loading State、Renderer Init State、Editor Tool State。减少大段 if/switch。状态类增多，切换关系需要清晰表达。
Strategy 策略把算法封装成可替换对象。排序策略、culling 策略、tone mapping 曲线、shadow filter。算法切换灵活。调用方需要知道策略差异。
Template Method 模板方法父类定义流程骨架，子类实现步骤。BasePass::execute 调用 setup/draw/cleanup。固定流程复用方便。依赖继承，不如组合灵活。
Visitor 访问者把操作从对象结构中分离。场景遍历、序列化、调试检查、统计收集。新增操作方便。新增元素类型困难，结构耦合较强。

04. 架构模式

架构模式回答“系统怎么分层、模块怎么通信、运行时对象怎么组织”。这些模式比 GoF 更接近引擎骨架。

Layering

Layered Architecture

把系统按职责分成 Platform、RHI、Renderer、Scene、Editor 等层。优点是边界清楚；代价是层太多会增加数据搬运。

Modules

Module System

Renderer、Asset、Input、Scene、Editor 等系统按模块初始化、更新和关闭。重点是依赖顺序和生命周期。

Scene

ECS

Entity 是 ID，Component 存数据，System 写逻辑。适合大量对象和批处理，但和传统 OOP 混用时要划清边界。

Scene

Scene Graph

用树表达父子层级和 Transform 继承。适合编辑器大纲、挂点和层级对象。

Render

Render Graph / Frame Graph

声明 pass 和资源依赖，由图决定顺序、临时资源和同步机会。代价是需要严格的资源声明。

Extensibility

Plugin System

导入器、编辑器工具、渲染后端通过插件注册。需要处理 ABI、版本和生命周期。

Dependency

Service Locator

通过全局注册表查找服务。使用方便，但容易隐藏依赖，适合 Logger、Profiler 这类工具服务。

Dependency

Dependency Injection

显式把 Device、AssetSystem、RenderGraph 等依赖传给对象。更清楚、更可测试，但构造链更长。

Events

Event Bus

系统级事件中心，用于 WindowResize、AssetReloaded、SceneLoaded。过度使用会让控制流难追踪。

Registry

Registry

集中注册 Component、Importer、Pass、Shader Param。适合数据驱动和插件化，但要处理初始化顺序和名字冲突。

Flow

State Machine

显式状态和转换管理 Engine Startup、Scene Loading、Swapchain Recreate、Editor Mode。

Messaging

Message Queue

通过队列传递跨线程或跨系统消息，例如 Main Thread 到 Render Thread。

05. 渲染专用模式

渲染专用模式回答“pass、材质、shader、descriptor、pipeline、临时资源和绘制项怎么组织”。这部分是渲染引擎自己的核心语言。

Pattern 解决的问题 典型用途 注意点
Render Pass Pattern把渲染流程拆成职责明确的步骤。ShadowPass、GBufferPass、LightingPass、BloomPass。pass 间资源和同步关系需要统一管理。
Render Graph声明 pass 的资源读写依赖。自动排序、资源别名、barrier 推导。需要严格的资源声明和调试工具。
Material / Material Instance材质模板和参数实例分离。M_ 定义 shader 和布局，MI_ 提供贴图和参数。参数校验、descriptor 更新和变体管理复杂。
Shader Reflection从 shader 反射绑定信息。自动校验 descriptor、uniform、push constant。依赖编译链和反射数据一致性。
Shader Permutation管理宏组合和 shader 变体。Normal Map、Skinning、Alpha Test、Debug View。组合爆炸，需要 cache 和裁剪策略。
Pipeline State Object Cache复用昂贵的 pipeline 创建结果。Vulkan graphics/compute pipeline 重用。key 必须完整且稳定。
Descriptor Set Cache复用 descriptor set 或 layout。材质贴图绑定、pass 输入输出。资源变化时失效规则复杂。
Bindless Resource Pattern用大资源数组和索引访问资源。大量纹理、材质表、GPU-driven rendering。需要 descriptor indexing 支持和严格生命周期。
Render Queue按用途组织绘制项。Opaque、Masked、Transparent、Shadow、PostProcess。分类边界和排序规则要稳定。
Sorting Key用整数 key 排序 draw item。pipeline/material/depth/pass 合成排序 key。key 位分配需要提前规划。
Frame Resource Pattern每帧独立资源避免读写冲突。uniform buffer、descriptor、command pool、fence。多帧资源增加内存占用。
Deferred Destruction QueueGPU 仍可能使用资源时延迟销毁。Image、Buffer、Pipeline、DescriptorPool。必须和 fence/timeline 绑定。
Upload Queue / Staging Context统一处理 CPU 到 GPU 上传。texture、mesh、buffer 初始化。同步和临时资源回收要谨慎。
Transient Resource临时 render target 自动分配和回收。bloom mip、postprocess intermediate、depth prepass。资源别名和同步更难调试。
Temporal History保存历史帧数据。TAA、SSR、motion blur、temporal denoise。需要 motion vector、history validation 和 resize 处理。
Debug Marker Pattern给 GPU 对象和 pass 加调试名字。RenderDoc、Nsight、Tracy、NVTX。需要贯穿资源创建和 pass 执行。
Hot Reload运行时重新加载 shader/material/texture。shader 迭代、材质调参、编辑器工作流。资源替换、失败回滚和线程同步复杂。
GPU-Driven RenderingGPU 生成或筛选 draw command。indirect draw、compute culling、meshlet。数据结构、同步和调试复杂度高。

06. 数据模式

数据模式回答“数据怎么保存、传递、引用、迁移和变更”。对于数据驱动渲染器，JSON/schema/asset manifest 往往比类继承更重要。

DTO

只承载数据，不承载复杂行为。适合 scene、material、mesh、terrain 配置结构。

Snapshot

捕获某一时刻的状态。适合场景保存、编辑器撤销、帧调试记录。

Serialization

把对象转换成可存储格式。适合 scene/material/render graph 配置。

Versioned Data

数据格式带版本并可迁移。适合 material JSON v1/v2、scene schema v1/v2。

Data-Driven Config

用外部数据驱动运行时对象。隐式约定必须文档化或 schema 化。

Prefab / Archetype

可复用对象模板。适合常用模型、灯光组合、材质默认配置。

Handle Pattern

用稳定 ID 引用资源。适合 TextureHandle、BufferHandle、MaterialHandle、Entity。

Sparse Set

用稀疏和密集数组存储组件。ECS component storage 常用。

SoA / AoS

按字段或对象组织内存。Transform、light、draw item 都会受数据布局影响。

Dirty Flag

只有数据变化时才重新计算。适合 Transform matrix、descriptor update、material upload。

Resource Manifest

记录资产路径、类型、依赖。适合 asset database、打包、热重载依赖追踪。

Stable ID

用长期不变 ID 关联数据。资产 GUID、编辑器对象、序列化引用都需要它。

07. 性能模式

性能模式回答“如何减少开销”。渲染引擎里不要把性能模式当装饰，它们通常直接影响系统边界。

Pattern 用途 收益 代价
Cacheshader reflection、pipeline、texture、sampler、mesh。避免重复计算和重复创建。失效策略和内存占用要控制。
Object Poolcommand、component、temporary draw item、粒子。减少频繁分配。生命周期和清理时机需要纪律。
Memory Pool小对象分配、组件存储、资源元数据。降低分配成本和碎片。实现和调试更复杂。
Arena / Linear Allocator每帧临时内存、render list、scratch data。极快，碎片少。不适合单个对象长期释放。
Ring Bufferdynamic uniform/storage buffer、upload buffer。适合 frames in flight。需要对齐、fence 和 wrap 处理。
Double / Triple Bufferingframe resource、swapchain、CPU/GPU shared data。提高并行度。增加内存和状态管理。
Batchingsprite、UI、same material draw、static mesh。减少 draw call 和状态切换。限制材质和排序自由。
Instancing大量相同 mesh、草、树、道具。大幅减少 draw call。需要 instance buffer 和 per-instance 数据布局。
CullingFrustum、Occlusion、Backface、Portal、Cluster。减少 GPU 工作量。CPU/GPU 剔除成本不能超过收益。
LODmesh LOD、texture mip、shadow cascade。控制远景成本。切换、过渡和资源制作成本。
Spatial PartitioningBVH、Octree、Grid、KD-Tree。加速 culling、ray query、light query。动态场景更新成本。
Lazy Loadingtexture、mesh、material、scene chunk。缩短启动时间。首次访问可能卡顿，需要占位资源。
Async Streaming大场景、贴图 mip、地形块。平滑加载，支持大世界。线程同步、优先级和失败回滚复杂。
SIMD / Data-Oriented Designskinning、culling、transform update。缓存友好，吞吐高。代码不如 OOP 直观。

08. C++ 惯用法

C++ 惯用法回答“如何正确表达所有权、生命周期和零成本抽象”。在 Vulkan 项目中，这一类通常比很多 GoF 模式更重要。

RAII

用对象生命周期管理资源获取和释放。管理 VkBuffer、VkImage、VkPipeline、file、mutex。

Rule of Zero / Five

明确资源类的拷贝、移动和析构规则，避免重复释放和悬空资源。

Move Semantics

转移资源所有权而非复制。资源 wrapper 的 moved-from 状态必须可析构、可赋值。

PImpl

隐藏 Vulkan 头和后端实现，降低编译依赖。代价是间接访问和堆分配。

CRTP

用模板实现静态多态。适合 typed handle、轻量 compile-time interface。

Type Erasure

保存不同具体类型但暴露统一接口。适合 job、asset importer、resource deleter。

Strong Typedef

区分 TextureHandle、BufferHandle、MaterialHandle，防止误传 ID。

Scope Guard

离开作用域自动执行清理动作，适合临时状态恢复和失败路径回滚。

Smart Pointer Ownership

unique_ptr 表示独占对象，shared_ptr 慎用于共享资源。

Intrusive Ref Count

引用计数放在对象内部，适合引擎资源，但对象侵入性强。

Span / View

非拥有数组视图。适合 vertex data、draw item list、descriptor writes。

Enum Flags

类型安全的 bit flags，适合 Vulkan 风格 usage、stage、access flags。

09. 并发与异步模式

并发模式回答“多个线程如何合作而不破坏资源生命周期和渲染顺序”。这部分一旦设计错，问题通常会表现成偶现卡顿、死锁、资源提前释放或渲染线程读到旧数据。

Pattern 用途 优点 风险
Job Systemculling、animation、resource import、scene update。利用多核，任务依赖可表达。调试和依赖图复杂。
Thread Pool后台加载、CPU 计算任务。避免频繁创建线程。任务粒度和阻塞策略要设计。
Producer-Consumerloader 线程生产资源，render 线程消费上传请求。解耦速度不同的系统。队列积压和退出流程要处理。
Double Buffered Stategame thread 写，render thread 读。避免直接竞争。数据同步点和延迟要明确。
Task Graphanimation -> culling -> command build。并行度更高，依赖显式。系统复杂度高。
Work Stealingjob system 调度。提高线程利用率。实现复杂，调试困难。
Future / Promiseasset loading、shader compilation。表达异步结果自然。等待位置可能造成隐藏阻塞。
Main Thread Affinitywindow、input、部分平台 API。避免平台限制问题。需要派发回主线程。
Render Thread渲染命令在专用线程构建或提交。game/render 解耦。资源同步和帧延迟更复杂。

10. Vulkan / GPU 工程模式

Vulkan/GPU 模式回答“CPU 写代码时如何尊重 GPU 的异步执行模型”。这部分是 Vulkan 学习最容易踩坑的地方。

CPU 视角

对象创建、命令录制、descriptor 更新、资源上传、等待 fence、提交 queue。

GPU 视角

命令异步执行、资源可能仍在使用、layout 和 access 必须匹配、跨 queue 需要同步。

Pattern 典型用途 解决的问题 注意点
Frames in Flight2-3 帧并行。提高 CPU/GPU 并行度。每帧资源复制，延迟增加。
Per-Frame Command Poolcommand buffer 管理。每帧整体 reset，简单高效。command buffer 生命周期必须绑定帧。
Per-Thread Command Buffer多线程 command recording。减少锁竞争。secondary command buffer 和合并顺序要设计。
Timeline Semaphorequeue sync、upload completion、frame pacing。用单调值表达同步进度。需要设备特性支持和清晰值管理。
Fence-Gated Reuseframe resource、staging buffer、descriptor pool。fence 完成后才复用资源。错误等待会造成 CPU/GPU stall。
Barrier Helperpass 之间资源状态转换。降低 Vulkan 同步样板。抽象错误会隐藏真正 hazard。
Resource State Trackingrender graph barrier 推导。跟踪 layout/access/stage。状态模型要覆盖 alias、external、swapchain。
Descriptor Layout Cache材质、pass、shader reflection。避免重复创建 layout。key 必须包含 binding 全信息。
Pipeline Layout Cachedescriptor layout + push constant 组合。复用 pipeline layout。和 shader layout 兼容性绑定。
GPU Deletion QueueVulkan handle 延迟释放。解决 RAII 与 GPU 异步冲突。队列泄漏会导致显存延迟释放。
Staging Upload Contexttexture、vertex/index buffer。上传路径统一。需要 batch 上传和同步策略。
Swapchain Recreationwindow resize、surface change。安全重建 swapchain 相关资源。老资源销毁必须等 GPU 完成。
Validation Layer Integrationdebug utils、best practices。快速定位 API 使用错误。debug 开销高，release 应可关闭。
Queue Ownership Transfertransfer queue -> graphics queue。充分使用专用队列。barrier 更复杂。
Push Constant Patterndraw index、material id、small params。小量频繁变化数据快速传递。大小有限，layout 兼容要注意。

12. 常见对比

比较页很适合做复习，因为很多概念名字相似，但解决的问题层级不同。

对比 区别
Factory vs BuilderFactory 选择创建哪种对象；Builder 管理复杂对象如何一步步创建。
Factory Method vs Abstract FactoryFactory Method 创建一种产品；Abstract Factory 创建一组相关产品。
Observer vs Event BusObserver 常是对象级依赖；Event Bus 是系统级事件中枢。
State vs State MachineState 是 GoF 对象行为模式；State Machine 是更通用的流程建模方式。
Memento vs SnapshotMemento 强调不破坏封装保存对象状态；Snapshot 更偏数据层状态记录。
Flyweight vs CacheFlyweight 共享内在状态以减少对象数量；Cache 保存昂贵结果以便复用。
RAII vs Deferred DestructionRAII 管 CPU 对象生命周期；Deferred Destruction 处理 GPU 异步使用后的真实销毁时机。
Scene Graph vs ECSScene Graph 擅长层级关系；ECS 擅长大量对象的数据布局和批处理。
Render Pass vs Render GraphRender Pass 是单个步骤；Render Graph 管理多个 pass 的依赖、资源和执行顺序。
Handle vs PointerHandle 更稳定、可验证、可序列化；pointer 直接但容易悬空。
shared_ptr vs Resource Handleshared_ptr 管共享所有权；resource handle 管资源表引用，通常更适合引擎资源。
Dirty Flag vs Immediate UpdateDirty Flag 延迟到需要时更新；Immediate Update 每次修改立即同步。
Cache vs PoolCache 复用计算或创建结果；Pool 复用对象或内存槽。
Descriptor Cache vs Descriptor AllocatorCache 关注复用已有 descriptor set；Allocator 关注从 pool 分配 descriptor set。
Timeline Semaphore vs FenceTimeline semaphore 可表达跨队列和跨帧进度；fence 常用于 CPU 等 GPU 完成。

14. 反模式提醒

这些不是“不能用”，而是要警惕它们在学习项目里慢慢把边界变模糊。

反模式 表现 风险
Pattern First先套模式，再找问题。代码复杂但没有收益。
God RendererRenderer 什么都知道、什么都做。难测试、难拆分、难扩展。
Global Everything到处用单例和全局访问。隐藏依赖，初始化顺序脆弱。
Stringly Typed Resource大量系统靠裸字符串传资源名。重命名、拼写和运行时错误多。
Shared Pointer Everywhere所有资源都用 shared_ptr。生命周期不清楚，资源释放不可控。
Immediate GPU Destruction析构时立刻销毁 GPU 资源。GPU 仍在使用时可能崩溃。
Over-Abstracted RHI学习项目过早抽象多后端。大量样板掩盖 Vulkan 学习重点。
Invisible Event Flow所有系统都靠事件总线通信。行为来源难追踪，调试困难。
Unbounded Cache缓存只增不减。内存和显存泄漏式增长。
Defensive Shader Runtime Fixupsshader 内做本应由数据源保证的修正。每帧执行无意义逻辑，掩盖数据错误。
