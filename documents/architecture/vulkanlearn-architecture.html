1) 已敲定约束（V1）

单 World 单 Game Thread 拥有写权限 可选 Render Thread（只读快照） WorldSubsystem 生命周期跟随 World 无过渡期，直接全量重构切换 Vulkan 唯一图形 API 无 API-neutral 设备过渡封装

这些约束是后续所有设计讨论的硬边界，新增方案不能违反它们。

本文档描述 VulkanLearn V1 的正式架构、当前完成基线和后续演进门槛。它的作用是把 main.cpp、engineLoop.*、rendererResourceLoadCoordinator.*、renderSystem.*、renderGraph.* 等现有职责重新划入稳定边界。

代码命名约定：UE-Lite 只作为前期架构路线名、文档背景和验收脚本名，不进入 C++ namespace。引擎侧新增代码统一放入 VL namespace，表示 Vulkan Learn / Vulkan Lite。

2026-06-04 同步结论：旧 RHIDevice 抽象接口和早期 tutorial render path 已从当前架构基线移除；source/render/rhi/vulkan/rhiDeviceVulkan.* 保留为 concrete Vulkan device boundary，RHIBufferHandle、RHIImageHandle 等 handle 只表示 Vulkan 资源生命周期 identity。后续扩展默认直接扩展 Vulkan-native backend / device boundary，不增加 DirectX/Metal/OpenGL 预留层、mock backend 或 API-neutral enum/createInfo/descriptor wrapper。

2) V1 范围与非目标

V1 必须完成
  • 建立 EngineLoop，让 main.cpp 只保留平台启动、窗口创建和顶层调度。
  • 把场景加载拆成 WorldLoader、WorldBuilder、WorldTransitionCoordinator 三段。
  • 让 World 成为 Gameplay 数据唯一归属，渲染层只读 WorldSnapshot。
  • 分离 RendererFrontend、FrameGraphCompiler、RendererBackendVulkan 和 RHIDeviceVulkan。
  • 把 Platform、Input、Console、Asset、Material、Shader、Config、Diagnostics 放进明确 subsystem 边界。
  • 明确 global / world-local / frame-local 资源 owner 与延迟释放规则。
V1 明确不做
  • 不引入 UObject、反射系统、GC、编辑器、蓝图、Cook/DDC 全套内容管线。
  • 不把 Actor/Component 做成复杂 ECS；保留学习项目可读性。
  • 不并行维护旧 scene/resource 执行路径和新 World 执行路径。
  • 不把 RHIDeviceVulkan 或 lifecycle handle 扩展成跨图形 API 的过渡封装。
  • 不在 shader 或每帧路径加入冗余防御逻辑；数据正确性由 JSON 校验和构建期保证。
  • 不把学习注释、必要报错、调试入口或仍有明确用途的 public 方法当作冗余清理掉。
  • 不借这次重构顺手改渲染算法、材质格式或资源目录命名。

设计原则：先把生命周期、所有权和数据边界固定，再在稳定边界内继续扩展渲染特性。

优化判定：冗余指旧执行路径、重复 owner、无调用且无计划用途的 API、以及会掩盖数据错误的 silent fallback；不包括用于学习 Vulkan/引擎边界的短注释、定位失败所需的结构化错误、debug/profiling/test hook、或已经进入架构合同的方法。

5) 设计模式与使用边界

V1 使用设计模式的目标是稳定依赖方向和生命周期，不是给每个类套模式名。优先选择能直接降低耦合、表达事务边界、隐藏 Vulkan 细节的模式；没有明确收益的抽象不进入 V1。

核心模式清单

模式 使用位置 解决的问题 使用边界
Facade EngineLoop、RendererFrontend、RendererBackendVulkan、RHIDeviceVulkan 给上层一个稳定入口，隐藏 SDL/Vulkan/pass/descriptor 的细节。 Facade 只收口调用，不拥有不属于自己的数据；不能变成新的大杂烩单例。
State Machine WorldTransitionCoordinator、swapchain recreate、engine lifecycle 让 Validate、BuildStaging、Swap、Retire、Failed 等阶段可追踪、可回滚。 只用于真实存在状态迁移和失败恢复的流程；普通顺序代码不用硬套状态机。
Builder WorldBuilder、WorldSnapshotBuilder、pipeline state 构建、render graph compile 把复杂对象构建过程拆成可校验步骤，避免半成品污染 active runtime。 Builder 输出完整对象或失败结果；不能边构建边修改 activeWorld。
Factory PipelineFactory、Actor/Component 创建、texture/buffer 创建、pass runtime 创建 集中处理创建参数、variant key、Vulkan create info 和兼容性。 Factory 不负责长期持有生命周期；创建后的 owner 必须明确。
Registry SubsystemCollection、AssetRegistry、shader/material library 提供按类型、名字或 key 查询的运行时目录，替代散落全局变量。 Registry 只做登记和查询，不直接驱动系统行为。
Command ConsoleSubsystem、CommandBus、debug/test commands 把 UI/控制台输入转成意图对象，避免控制台直接改 World 或 Renderer 内部状态。 Command 必须有参数校验和目标 owner；不能携带裸指针跨帧执行。
Observer / Event Bus OnWorldChanged、swapchain resize event、debug option changed 让系统响应生命周期事件，而不是互相直接调用深层实现。 事件只传稳定数据或句柄；不传可变 World 指针给渲染层。
Snapshot / DTO WorldSnapshot、RenderScene、CompiledFrameGraph 跨线程和跨层传递冻结数据，切断 Renderer 对 Gameplay 对象的直接依赖。 Snapshot 构建后只读；禁止藏 mutable Actor/Component 引用。
Flyweight / Cache mesh section、texture、shader variant、pipeline、global resources 用稳定 key 复用重资源，避免 scene reload 重复创建昂贵对象。 cache key 必须包含影响结果的全部参数；释放仍走 retire epoch。
RAII Vulkan device boundary、GPU buffer/image/image view/sampler、descriptor pool/set、render pass、framebuffer 让 C++ 对象表达 Vulkan 资源 ownership，减少泄漏和重复 destroy。 RAII 析构不能无视 GPU in-flight；需要结合 ResourceRetireQueue。
Boundary Facade Renderer frontend/backend 与 Vulkan device boundary 让渲染意图、frame policy 和底层 VulkanManager/global device state 分离，保留 Vulkan 学习项目的原生 API 表达。 V1 只有 Vulkan 实现，不为了“多后端想象”提前制造复杂接口层。
Strategy shadow projection strategy、debug view mode、tone mapping preset、resource upload policy 把少数可替换算法变成显式策略，减少 if/else 在渲染主流程中膨胀。 策略数量少时可以先用 enum + named helper；不急着全虚函数化。

6) Platform / Engine / Input

PlatformApplication

负责 SDL 初始化、窗口创建、事件 pump、鼠标捕获、窗口 resize、退出事件。它不认识 World、Material、RenderGraph。

当前落点：source/platform/platformApplication.* 负责 SDL init/quit、Vulkan loader、extension 查询和事件翻译；窗口尺寸由 PlatformApplicationDesc 注入，不再由平台层读取 CommonFunction 配置。

EngineLoop

唯一顶层调度器，负责 Init -> Tick -> Shutdown，把平台事件、命令、World tick、snapshot、render submit 串起来。

当前落点：source/engine/engineLoop.* 只编排 shader 编译、Vulkan 初始化后的资源加载、初始 World、调试控制台、Controller、事件泵、更新渲染循环和 GPU idle shutdown；Shader monitor/worker/pending-source 状态由 ShaderReloadRuntime 持有，World/Graph 候选 prepare 与原子 commit 由 WorldGraphTransactionCoordinator 持有，跨 World 的 RuntimeClock、FpsTool、InputSubsystem、WorldManager 由 SubsystemCollection 持有。

GameInstance

跨 World 生命周期的上下文，持有 EngineSubsystem、WorldManager、CommandBus、全局配置，不持有具体 Actor。

当前落点：source/engine/gameInstance.* 已持有 RuntimeConfig 引用和强类型 SubsystemCollection；CommandBus、ConsoleSubsystem、RuntimeClock、FpsTool、InputSubsystem、WorldManager 均由集合持有。

InputSubsystem

把 SDL 键鼠事件转成 InputActionState，Controller 消费 intent。切换 World 后重新绑定 active camera。

当前落点：source/input/inputSubsystem.* 已集中处理键盘状态、相对鼠标位移和 mouse capture；controller.* 不再直接 include SDL。

事件与输入流

SDL Event
  -> PlatformApplication::PollEvents()
  -> PlatformEvent queue
  -> EngineLoop::PumpPlatformEvents(current)
  -> InputSubsystem::UpdateActionState(current)
  -> CommandBus::QueueCommand(optional target)
  -> PlayerController::ApplyToActivePawnOrCamera
  -> WorldSnapshotBuilder exports final camera state
场景 职责归属 设计约束
窗口 resize Platform 发 resize event；EngineLoop::RecreateRendererForWindowResize() 以 wait-idle 的保守事务重建 swapchain、RenderGraph render targets/render pass/framebuffer、frame UBO/light SSBO、material UBO、object descriptor。 resize 不触发 World reload，不销毁 Gameplay 数据。
Esc 鼠标捕获切换 InputSubsystem 修改 capture 状态；PlatformWindow 执行实际 SDL window 调用。 Controller 不直接操作窗口系统，也不读取 SDL 键鼠状态。

7) Asset / Material / Shader

这部分是 World 与 Renderer 之间最容易重新耦合的区域。V1 要把“资产解析”和“GPU 可用资源”拆成两层：Asset 层输出描述，Resource / Vulkan Backend 层负责创建和释放。

模块 职责 输出 禁止
AssetManager 统一加载 JSON、mesh descriptor、terrain descriptor、texture asset、material instance，生成稳定 cache key。 AssetLoadPlan、CPU-side asset data、依赖列表 直接创建 Vulkan image/buffer/pipeline
ShaderLibrary 管理 shader source、SPIR-V 编译结果、反射数据、variant key 和错误报告。 ShaderReflection、ShaderVariantHandle 在每个 material instance 里重复编译同一 shader
MaterialLibrary 管理 M_ 基础材质、MI_ 实例、参数默认值、贴图绑定和 pass 兼容性。 MaterialDesc、MaterialInstanceDesc、PipelineVariantKey 把 pass descriptor 或 frame resource 塞回 Asset 层
PipelineFactory 按 render pass compatibility、sample count、shader variant、pipeline state 创建或复用 pipeline。 PipelineHandle、descriptor set layouts、shader binding layout 反向查询 World 或 renderer resource cache 内部状态
TextureUploadService 把 texture asset 描述变成 GPU texture，并记录 layout、sampler、descriptor image info。 TextureHandle、DescriptorImageInfo 在材质校验阶段上传 GPU 资源

材质与 shader 数据流

shader/glsl + material JSON
  -> MaterialParameterIncludeGenerator
  -> ShaderCompiler + ShaderReflection
  -> MaterialInstanceValidator
  -> PipelineFactory(PipelineVariantKey)
  -> RendererFrontend builds binding requests
  -> FrameGraph/Backend writes descriptor sets

绑定规则：shader reflection 是材质参数和 descriptor binding 的真实裁判；JSON 负责提供正确数据，运行时渲染路径不做重复兜底。

数据正确性边界：scene object type 必须在 scene validation 阶段识别；mesh asset materialSlots 必须是非空有序数组，并且数量与源模型 material slot 数一致。未知 scene object type、缺失 slot、slot 数不一致或 section 无法按源 slot 序号映射，都应加载失败；禁止用 unsafe fallback material 或 renderer 侧静默跳过掩盖资产错误。

加载错误域：scene / mesh validation 失败在 WorldLoader 边界归类为 Scene.LoadFailed 或 Mesh.LoadFailed；renderer resource load 阶段失败在 WorldTransitionCoordinator 边界归类为 Material.LoadFailed、Texture.LoadFailed、Mesh.LoadFailed、Shader.LoadFailed 或保底 WorldTransition.LoadFailed。

8) Renderer / Vulkan Backend / FrameGraph

Renderer 不是一个大类，而是三段：Frontend 组织渲染数据，FrameGraph 编译 pass/resource，Backend / Vulkan device boundary 执行 Vulkan。

图形 API 策略：VulkanLearn V1 以 Vulkan 作为唯一图形 API。代码中保留的 RHIDeviceVulkan、RHIBufferHandle 等名称是历史命名和资源生命周期 handle 语境，不代表跨 DirectX/Metal/OpenGL 的抽象层；后续扩展优先增加 Vulkan-native backend 能力，而不是把 vk::* enum、createInfo 或 descriptor info 包成 API-neutral 类型。

渲染设备边界处置状态：已删除旧 source/render/rhi/rhiDevice.h 虚接口；当前 source/render/rhi/ 目录只承载 Vulkan device boundary 与 lifecycle handle 定义。若以后清理命名，应作为一次机械命名迁移单独处理，而不是借机恢复多后端抽象。

层 负责 输入 输出
RendererFrontend 把 WorldSnapshot 转成按 pass/material/mesh 分组的 RenderScene。 WorldSnapshot、debug view、render options draw packets、light data、camera data、material binding requests
ResolvedRenderSceneBuilder 当前实现中的后端解析层：把 RenderScene 的逻辑 handle 解析成当前 Vulkan draw path 需要的 material、materialInstance、renderable object 与 backend object resource entry；resolved draw packet 不再保留 SceneObject 引用。 RenderScene、RendererResourceCache ResolvedRenderScene；包含 resolved draw packet 与 backend object resource entry

12) WorldSnapshot 生成与消费（GT -> RT）

WorldSnapshot 可以理解为 GT 给 RT 的一帧只读渲染订单。它不是复制整个 World，而是在 GT 仍然拥有 mutable World 的时刻，把渲染需要的 camera、draw、light、environment 和逻辑资源句柄导出成不可变 DTO，再通过一个 latest-wins mailbox 交给渲染侧消费。

关键点：RT 不是“安全地读 World”，而是“完全不读 World”。RT 只读 shared_ptr<const WorldSnapshot>，再把它翻译成自己的 RenderScene。

先用代码视角理解 snapshot

这里的 snapshot 更像相机快门，而不是存档系统：GT 在一个确定时刻按下快门，把“这一帧渲染要用的数据”拍成不可变结构；之后 GT 可以继续 tick、移动物体、切换 World，RT 手里的旧 snapshot 仍然是一份完整、独立、只读的渲染输入。

对象 代码角色 一句话理解 线程意义
WorldSnapshotBuilder 只在 GT 读取 World，复制 camera、draw、light、environment。 采样器：把 mutable World 采成值类型 DTO。 跨线程前最后一次接触可变 Gameplay 数据。
WorldSnapshot 保存矩阵、bounds、灯光参数、环境参数和 ResourceHandle。 渲染订单：这帧要画什么、用什么逻辑资源画。 没有 World*、SceneObject*、Vk*，天然适合跨线程只读传递。
WorldSnapshotQueue 用一个 mutex 保护 latestSnapshot 指针槽。 邮箱：永远只留最新一封渲染订单。 GT 发布和 RT 取走只交换 shared_ptr<const WorldSnapshot>，重活都在锁外。
RendererFrontend 把 WorldSnapshot 转成 RenderScene 和 draw packet 分组。 翻译器：World 形状的数据变成 Renderer 形状的数据。 RT 后续只理解渲染域结构，不再回头读 World。 
// GT: snapshot is built while World is still owned by the game side.
WorldSnapshot snapshot = worldSnapshotBuilder.Build(activeWorld, buildDesc).Value();
snapshotQueue.Publish(std::move(snapshot));   // becomes shared_ptr<const WorldSnapshot>

// RT: snapshot is consumed as immutable input.
std::optional<WorldSnapshotPtr> snapshot = snapshotQueue.ConsumeLatest();
if (snapshot.has_value()) {
    RenderScene scene = rendererFrontend.BuildRenderScene(**snapshot).Value();
    backend.RecordAndSubmit(scene);
}

所以它有趣的地方在于：同步点只发生在“指针交接”上，而不是“让 RT 读 World”上。GT/RT 之间传递的是不可变值对象的所有权引用，渲染资源解析和命令录制都发生在渲染域内部。

把它当成线程协议看

这套设计的核心不是“WorldSnapshot 这个结构体很大”，而是它把跨线程关系降级成一次消息传递：GT 负责生产一条完整消息，RT 负责消费这条消息。消息发出以后，GT 不再修改它；RT 也不需要知道这条消息来自哪个 Actor、Component 或加载器。

协议阶段 谁拥有数据 允许做什么 禁止做什么
GT Tick 中 GT 拥有 mutable World 更新 Actor/Component、相机、灯光、场景切换状态。 RT 读取 World 或缓存 SceneObject*。
Build snapshot GT 暂时读取 World，创建值类型 DTO 复制矩阵、bounds、灯光、环境参数和逻辑资源 key。 把可变对象指针、Vulkan 对象或 loader 状态塞进 snapshot。
Publish mailbox WorldSnapshotQueue 短暂拥有指针槽 用 mutex 替换一个 shared_ptr<const WorldSnapshot>。 在锁里遍历 World、解析资源、创建 GPU 对象。
RT consume RT 持有自己的 shared_ptr<const WorldSnapshot> 构建 RenderScene、解析资源、录制当前帧命令。 回头询问 World 当前状态，或修改 snapshot。

所以它能给渲染线程消费，不是因为给 World 加了很多锁，而是因为跨线程交接点上已经没有 mutable World 了。

实现机制拆开看

这个 snapshot 不是把 World 做深拷贝，也不是给 RT 一个加锁后的 World 视图。它更像一次“渲染输入采样”：GT 在一个确定时刻读取 active World，把 RT 需要的值复制到线性 DTO 中；复制完成以后，这份 DTO 就脱离 World 生命周期，由 shared_ptr<const WorldSnapshot> 管理。

步骤 源码落点 具体做什么 为什么这样做
1. 校验帧上下文 WorldSnapshotBuilder::Build 确认 desc.worldGeneration 与 active World 一致，并要求场景存在 active camera。 避免 World 切换过程中把旧 generation 的输入误交给新渲染场景。
2. 冻结 camera CameraSnapshot 复制 view/projection/viewProjection、位置、方向、裁剪面，并保存上一帧 previousViewProjection。 RT 录制多个 pass 时看到的是同一台相机；后续 TAA/motion vector 也能拿到历史矩阵。
3. 冻结 draw 输入 MeshDrawSnapshot 按 stable object id 复制 model/previousModel、world bounds、mesh/material/materialInstance 的 ResourceHandle。 GT 下一帧移动 Actor 不会改变 RT 正在录制的 draw packet。
4. 冻结 lights/env LightSnapshot、EnvironmentSnapshot 复制灯光参数、worldToLight、IBL 逻辑 key、SH 和 intensity。 shadow、lighting、post-process 看到同一批光照输入。
5. 发布指针 WorldSnapshotQueue::Publish 把 DTO 包成 shared_ptr<const WorldSnapshot>，只在 mutex 内替换 latestSnapshot 指针槽。 锁的粒度极小；不会在锁内遍历 World 或构建渲染资源。
6. 渲染侧翻译 RendererFrontend::BuildRenderScene 消费 snapshot，校验 ResourceHandle，把 mesh draw 转成 RenderDrawPacket，再按 material/materialInstance 分组。 让 RT 拿到 Renderer 形状的数据，而不是继续理解 World 的 Actor/Component 结构。

为什么不是直接双缓冲 World

直接双缓冲 World 看起来也能让 RT 读旧帧，但代价很高：World 里会混进 gameplay 状态、资源加载状态、component 生命周期和外部指针，拷贝边界不清晰。V1 选择只 snapshot 渲染输入，等于把跨线程合同压缩到一个小而明确的数据包。

ResourceHandle 是这套机制的关键

Snapshot 里不放 VkImage、VkBuffer、descriptor set，也不放 SceneObject*。它只放资源逻辑 key，例如 mesh name、material key、material instance name、environment key。RT 拿到 snapshot 后，再由渲染侧的 ResolvedRenderSceneBuilder 和 RendererResourceCache 把这些 key 解析成当前 backend 可用的 GPU entry。

Mailbox 最小实现

WorldSnapshotQueue 不是会积压很多帧的普通队列，而是一个只保留最新快照的 mailbox。GT 发布新快照时覆盖未消费旧快照；RT 消费时把指针拿走，后续构建 RenderScene 的重活全部在锁外完成。

// source/world/worldSnapshot.cpp 的核心形态
void WorldSnapshotQueue::Publish(WorldSnapshot snapshot)
{
    Publish(std::make_shared<const WorldSnapshot>(std::move(snapshot)));
}

void WorldSnapshotQueue::Publish(WorldSnapshotPtr snapshot)
{
    std::lock_guard<std::mutex> lock(mutex);
    latestSnapshot = std::move(snapshot);       // latest-wins
}

std::optional<WorldSnapshotPtr> WorldSnapshotQueue::ConsumeLatest()
{
    std::lock_guard<std::mutex> lock(mutex);
    if (!latestSnapshot)
    {
        return std::nullopt;
    }

    WorldSnapshotPtr snapshot = std::move(latestSnapshot);
    latestSnapshot.reset();
    return snapshot;                            // consumer works outside the lock
}
动作 锁保护什么 锁外发生什么 语义
Publish 只保护 latestSnapshot 指针槽。 遍历 World、构建 snapshot、计算 bounds 都已经完成。 发布最新一帧；旧的未消费帧可以被覆盖。
ConsumeLatest 只保护“取走并清空 mailbox”这个动作。 构建 RenderScene、解析资源、录制命令。 消费者拿到自己的 shared_ptr<const>，旧快照不会悬空。
PeekLatest 只读观察指针槽。 调试或诊断。 不用于跨线程所有权转移。
Clear 清空 mailbox 指针槽。 RT 已持有的 snapshot 仍由 shared_ptr 延寿。 适合 shutdown、切 World 或失败回滚前清理未消费帧。

为什么 RT 能消费：它读的是消息，不是对象

RT 拿到 snapshot 之后，看到的是一份冻结的渲染输入消息。GT 可以继续进入下一帧，甚至切换 World；RT 手里的旧消息仍然由自己的 shared_ptr<const> 延寿，内容也不会再变化。

没有可变 World 引用

Snapshot 里只有矩阵、向量、数组、bounds、light 参数和 ResourceHandle。RT 看不到 World*、Actor*、SceneObject*。

类型上只读

WorldSnapshotPtr 是 std::shared_ptr<const WorldSnapshot>。RT 拿到后不能改，GT 发布下一帧也不会改这份旧对象。

生命周期独立

GT 覆盖 mailbox 只替换队列里的指针槽。RT 已经拿走的旧 snapshot 会活到 RT 释放自己的 shared_ptr。

GPU 资源仍归渲染层

Snapshot 只带逻辑 ResourceHandle。材质、mesh、texture、object buffer、descriptor 继续由 RendererResourceCache、Backend 和 Vulkan device boundary 管。

慢 RT 的 latest-wins 行为

GT publishes snapshot A
RT consumes A and starts BuildRenderScene(A)

GT publishes snapshot B while RT still holds A
  mailbox now points to B
  A is still alive because RT owns shared_ptr(A)

GT publishes snapshot C before RT consumes B
  mailbox replaces B with C
  B can be released if nobody else holds it

RT finishes A, then consumes latest snapshot
  RT gets C, not stale B

实时渲染通常更关心最新状态，而不是把过期帧全部排队提交。这个 mailbox 语义会牺牲“每帧必达”，换来低延迟和清晰生命周期。

    TickWorld(activeWorld);

        snapshotQueue.ConsumeLatest();

        SubmitLastGoodRenderSceneOrIdle();
        continue;

    if (renderScene.IsSuccess()) {

    }

13) 线程与数据边界图（V1）

关键约束：World 只在 GT 写；RT 只读取 RenderScene 快照；交接只通过 SnapshotQueue。V1 不引入线程池或 TaskGraph，CPU 线程预算只由 config/config.json -> workerThreadCount 控制。

workerThreadCount 的 V1 语义：缺省按 1 处理；1 表示完全同步，只运行 GT / main thread；2 表示 GT + 专用 RT；0、负数和 > 2 都是配置错误；旧的 renderThread.enabled 配置视为废弃字段并报错。后续 JobSystem / TaskGraph 才会扩展 > 2。

16) 资源与 GPU 生命周期

当前代码里 RendererResourceLoadCoordinator、ResolvedRenderSceneBuilder、RenderGraph 和 RenderSystem 都会间接碰到材质、贴图、descriptor 和 pass 资源。V1 需要继续按 owner 拆开，否则 World 切换仍然会产生隐式悬空引用。

当前实现把资源表集中到 RendererResourceCache 并拆出 global / world-local 清理边界。RendererResourceLoadCoordinator 可以向隔离的 candidate cache package 加载 material、texture、mesh/renderable 与 environment 资源，并把纯数据 MeshObjectBuildPlan 汇总到 RendererWorldResourceLoadResult；WorldTransitionCoordinator::PrepareWorldLoad() 使用该 package 构建 staging World。candidate 继承已有 process-global texture identity；初始 candidate 可以 lazy 创建缺失的 BRDF LUT，CommitCandidate() 与 World-local package 一起发布这些首次全局绑定。已存在的 global binding 不允许被候选替换或删除，相关冲突在 prepare 阶段失败。WorldGraphTransactionCoordinator 再把 candidate package 与 PreparedRenderGraphState、pipeline cache candidate、runtime binding、正式 Shader artifact/include publication 和退休记录组成单一事务。prepare 不触碰 active cache；最终 live publication 是预校验后的 ownership move/swap，成功后才激活退休。普通材质贴图上传、mesh vertex/index buffer 上传、BRDF LUT、environment cubemap/prefilter 与 Texture/RenderableObject 销毁仍走 RendererBackendVulkan 门面，底层 Vulkan 生命周期由 RHIDeviceVulkan 和对应 lifecycle handles 管理。

Retire Epoch 规则

  • 当前 RendererBackendVulkan::SubmitFrame 在 backend 内部生成 submittedEpoch，submit 后记录到 frame fence 槽；下一次复用该 fence 前把对应 epoch 交给 ResourceRetireQueue::CollectCompletedEpoch()。
  • world-local 资源释放请求进入 ResourceRetireQueue，队列用 shared_ptr<void> 延寿已有资源对象，避免 GPU in-flight 时触发 Vulkan destroy。
  • retire 条件为 resource.lastUsedEpoch <= completedEpoch；shutdown 时先 device.waitIdle()，再 ForceReleaseAll() 清空退役队列。
  • 开发期记录资源名、owner generation 和 epoch，方便定位泄漏。

Shader 增量构建与热重载线程/数据流

正式合同见 documents/rendering/shader-build-cache.md 与 documents/rendering/shader-hot-reload.md；本节只记录与本架构文档相关的线程归属与资源生命周期。

GT (EngineLoop -> ShaderReloadRuntime)
  -> ShaderFileMonitor::Poll（observed source epoch + debounce stable event）
  -> stable source identity 合并进 pending union
  -> worker idle 时捕获 live recipe 与 frozen primary/include snapshot
  -> ShaderCompileWorker（纯 CPU：shaderc + 反射 + ABI 校验，不触 Vulkan / live cache / manifest）
GT 更新边界
  -> source epoch 快速拒绝过时 candidate
  -> 提交前复核全部 primary/dependency digest
  -> WaitForRenderThreadIdle 安全点创建 Vulkan Pipeline / descriptor package
  -> 事务提交 Material Surface/Shadow、Compute、UI 引用
  -> 旧 Pipeline/descriptor/UI 资源进 ResourceRetireQueue
  -> 等待 GPU frame epoch 完成后析构

WorldGraphTransactionCoordinator 让启动 World、运行时 World reload 与 M_*.json 定义变化共用候选事务：解析、候选 generated include、World-local resource package、PreparedRenderGraphState、Material/MI descriptor package、resolved scene 与 view target 都在 staging owner 中完成。启动在事务前只建立 candidate prepare 所需的 RenderSystem 基础资源，事务成功后才初始化 UI overlay。初始 candidate 首次产生的 process-global texture binding 与 World-local package 一起发布，后续候选只能继承相同 global identity。prepare 不修改 active owner；全部可失败工作结束后，正式 artifact/include 发布和 World/resource/graph/RenderSystem/Controller 的 ownership move/swap 进入 no-throw commit。任一 prepare 失败时旧 World、graph、runtime binding 与正式文件保持，成功 swap 后才激活 PreparedResourceRetirements 或 PreparedRetiredResourcePackage::Activate()。

worker 在 Vulkan teardown 前 stop + join，完成但尚未提交的 candidate 会被丢弃，不得在 teardown 后回调。验证入口：--shader-reload-test、--shader-auto-reload-test、--shader-compute-reload-test、--shader-definition-reload-test、--shader-ui-reload-test、--shader-shutdown-inflight-test、--world-graph-transaction-test；运行时验证共享 shader/spv/，必须串行执行。
